# 资产识别与价格逻辑

## 1. 这份文档是干什么的

这份文档专门讲一件事：

`系统是怎么识别一只资产，并决定去哪里拿价格的。`

你可以把它理解成一条完整链路：

1. 用户输入一个代码
2. 系统先把代码标准化
3. 再判断它属于 A 股、港股、美股还是基金
4. 再判断它默认应该是什么币种
5. 最后按资产类型去不同的数据源取价格

这份文档就是把这 5 步讲清楚。

---

## 2. 先看总原则

系统内部最核心的资产分类只有 4 类：

- `a` = A股
- `hk` = 港股
- `us` = 美股
- `fund` = 基金

你现在只要先记住这张最粗的表：

| 输入或前缀 | 系统归类 |
| --- | --- |
| `sh / sz / bj` | A股 |
| `hk / .HK / 5位数字` | 港股 |
| `gb_ / 纯字母` | 美股 |
| `f_纯数字 / ft_` | 基金 |
| `f_字母` | 纠偏成美股 |

注意：`f_纯数字` 有明确号段例外。`f_60xxxx/f_68xxxx` 是误标沪市股票；
`f_15xxxx/f_18xxxx/f_50xxxx/f_51xxxx/f_52xxxx/f_56xxxx/f_58xxxx` 走场内行情。
统一规则在 `core/parser.py`，不再以行情接口当天是否成功决定这些代码的身份。

## 3. 第一步：代码怎么标准化

这一步代码在：

- [parser.py](/Users/kona/Desktop/kaka/kona_repo/kona_tool/core/parser.py)

作用很简单：

`把用户输入的各种写法，统一改成系统内部认得的格式。`

### 3.1 纯数字输入

#### 5 位纯数字

默认按港股处理。

例如：

- `00700 -> 00700.HK`

默认币种：

- `HKD`

#### 11 开头的 6 位数字

默认按基金处理。

例如：

- `110018 -> f_110018`

#### 16 开头的 6 位数字

也按基金处理。

例如：

- `161907 -> f_161907`

#### 6 / 5 / 9 开头的 6 位数字

按沪市处理。

例如：

- `600000 -> sh600000`
- `511360 -> sh511360`
- `900901 -> sh900901`

#### 0 / 3 / 1 / 2 开头的 6 位数字

按深市处理。

例如：

- `000001 -> sz000001`
- `159655 -> sz159655`
- `200002 -> sz200002`

#### 4 / 8 开头的 6 位数字

按北交所处理。

例如：

- `830001 -> bj830001`

### 3.2 港股格式

如果输入本来就带 `.HK`，那按港股处理。

例如：

- `00700.HK`

### 3.3 纯字母

纯字母默认按美股处理。

例如：

- `AAPL -> gb_aapl`

## 4. 第二步：系统怎么判断市场分类

这一步代码在：

- [asset_type.py](/Users/kona/Desktop/kaka/kona_repo/kona_tool/core/asset_type.py)

真正页面里看到的分类，是下面 4 类：

- A股
- 港股
- 美股
- 基金

### 4.1 A股

这些都会被归到 A股：

- `sh...`
- `sz...`
- `bj...`

也就是说：

- 普通 A 股股票算 A股
- 场内 ETF 只要是 `sh/sz` 开头，也算 A股
- 北交所也暂时放在 A股

一句话：

`只要是 sh / sz / bj 开头，系统就归到 A股。`

### 4.2 港股

这些会被归到港股：

- `hk...`
- `xxxx.HK`
- 5 位纯数字

例如：

- `hk00700`
- `00700.HK`
- `00700`

一句话：

`5位数字或 hk / .HK，都按港股。`

### 4.3 美股

这些会被归到美股：

- `gb_...`
- 纯字母代码
- 被误写成 `f_` 但后面其实是字母的代码

例如：

- `gb_aapl`
- `AAPL`
- `f_NUGT`

这里有个很重要的纠偏规则：

`f_` 不等于一定是基金。`

`f_` 后面是纯数字时，还要排除前面列出的明确交易所号段。

如果是：

- `f_NUGT`
- `f_BOXX`

这种字母型 `f_`，系统会认为这是误标，最后按美股处理。

### 4.4 基金

这些会被归到基金：

- `f_` 开头并且后面是纯数字，且不属于明确的交易所号段
- `ft_...`

例如：

- `f_110018`
- `f_161907`
- `ft_LU1116320737`

一句话：

`f_纯数字 和 ft_ 都算基金。`

## 5. 第三步：系统怎么判断默认币种

币种规则主要在：

- [parser.py](/Users/kona/Desktop/kaka/kona_repo/kona_tool/core/parser.py#L11)

注意：

`市场分类` 和 `币种` 不是一回事。

但系统会根据代码强制给一些币种规则。

### 5.1 强制币种规则

- `sh900xxx` -> `USD`
- `sz200xxx` -> `HKD`
- `gb_...` -> `USD`
- `ft_...` -> `USD`
- `hk...` 或 `.HK` -> `HKD`
- `sh / sz / bj / f_` -> `CNY`

### 5.2 重点理解

这里最容易搞混的是 B 股：

- 沪 B：`sh900xxx`，虽然也是 `sh`，但币种不是人民币，是 `USD`
- 深 B：`sz200xxx`，虽然也是 `sz`，但币种不是人民币，是 `HKD`

所以系统对 B 股有专门优先规则，不让它们被普通 `sh/sz` 逻辑覆盖掉。

## 7. 特殊情况

### 7.1 场内 ETF 被错存成 `f_`

有些资产虽然代码写成了 `f_`，但本质上是场内交易基金。

例如：

- `511360`

这类明确号段，系统会直接在取价与新增入口纠正成交易所代码，比如：

- `sh511360`

即使行情源暂时不可用，也不回退成场外基金净值或新建错误的 `f_` 身份。
`16xxxx` 仍保留原来的场内报价验证：验证成功才走场内，失败保留基金口径。

对应代码：

- [_exchange_fund_candidates](/Users/kona/Desktop/kaka/kona_repo/kona_tool/core/price.py#L172)
- [_map_fund_code_to_exchange_if_tradable](/Users/kona/Desktop/kaka/kona_repo/kona_tool/core/price.py#L188)

一句话：

`明确场内号段固定走场内；有歧义的 16xxxx 保留验证。`

#### 历史别名与新增防重（2026-11-19，本地源码修复）

- 达仁堂 `f_600329` 和光大银行 `f_601818` 取价时分别解析为 `sh600329/sh601818`，但批量报价返回键仍保留原代码。
- `get_asset_trend` 复用相同映射，返回原 `code` 和行情 `resolved_code`，历史趋势走股票收盘链路，不走基金净值。
- 交易市场、实时指标、分析拆分和快照的净值等待判断按真实行情身份走；旧股票不能继续因 `asset_type=fund` 等待净值。ETF 交易市场为 A 股，产品统计仍可为基金。
- 新增和现金买入按“同用户、同账本”检查双向别名。只有一条已有持仓时沿用旧行代码，不批量改持仓和交易记录；全新资产用规范代码。
- 普通新增保持原有覆盖数量/成本语义，现金买入保持加仓语义，不自动把两条已存在的别名持仓合并。两条都存在时返回 `409 / AMBIGUOUS_ASSET_ALIAS`，写入前停止。
- 匿名且未传账本的旧入口继续按 `ledger_id=0` 工作，不增加 `LEDGER_REQUIRED` 限制。
- 普通加仓、减仓、修改、删除仍要求使用持仓接口返回的原始 `code`；它们没有新增自动换码。旧持仓继续返回 `f_600329` 时，以该代码操作能保留交易关联，不应由客户端自行替换成 `sh600329`。
- 不把 `f_000001`、ETF 联接基金、`968xxx` 或 ISIN 基金按名称硬改成股票。
- 本轮只修源码，不迁移数据库、不发布、不回写历史快照。旧巡检的误标提示仍可能存在，不能把取价兼容误称为数据库已清理。

回归测试：`tests/test_price_identity_regression.py` 覆盖线上巡检的全部 23 种场内基金代码和两条股票，
`tests/test_price_alias_api_regression.py` 用真实请求与临时数据库覆盖新增、旧代码加减仓、现金买入及账本隔离。

### 7.2 `968xxx` 为什么特殊

因为这类海外基金经常出现：

- 天天基金慢半拍
- 腾讯 `jj` 口径不稳
- 东财 F10 不一定总能给到

所以现在规则是：

- 东财确认净值优先
- 东财拿不到时，`968xxx` 优先走 overseas 海外基金页

目的是尽量避免拿到旧值。

### 7.3 `ft_` 为什么和普通 `f_` 不一样

因为 `ft_` 这类基金更依赖：

- 基金公司官方页
- 海外财经站点

所以系统不会把 `ft_` 和普通 `f_` 放在一套基金逻辑里处理。

## 9. 当前结论

你只要先记住这几句就够了：

1. `sh / sz / bj` 都按 A股处理。
2. `hk / .HK / 5位数字` 都按港股处理。
3. `gb_` 和纯字母代码按美股处理。
4. `f_` 只有后面是纯数字时才真的是基金。
5. `ft_` 是特殊基金，优先看官方。
6. 普通基金优先看确认净值，不优先信估算值。
