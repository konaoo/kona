# 线上运维与发布操作图

这份文档只讲一件事：

`从你提一个需求，到代码改完、验收、推 GitHub、看 Actions、到腾讯云生效，这条链到底怎么走。`

这不是给运维工程师考试用的，而是给你自己以后也能照着走的操作图。

---

## 1. 先说结论

你这个项目当前有两条“上线生效”路径：

### 路径 A：正式路径

```text
本地改代码
-> 本地验收
-> 你确认通过
-> 写版本记录
-> 推 GitHub
-> 看 Actions
-> 合主干 / 触发部署
-> 线上生效
```

这条适合：

- 正式功能修改
- 要留代码记录
- 要让仓库和线上一致
- 要长期保留

### 路径 B：应急路径

```text
本地改代码
-> 直接发腾讯云
-> 重启服务 / 重打快照 / 改线上数据
-> 线上立刻生效
```

这条适合：

- 紧急修 bug
- 数据修复
- 线上排障
- 临时补救

但问题也很明显：

`如果后面不补回 GitHub，仓库和线上就会分叉。`

## 4. GitHub 这条线怎么理解

### 4.1 推分支

推分支的作用是：

- 先把代码安全放到 GitHub
- 不直接污染主干
- 不直接触发主干部署

适合：

- 改动还没最终确认
- 你只想先暂存
- 改动分几块，不想一锅端

### 4.2 合主干

代码真正进入 `main`，才代表：

- 仓库正式接纳这次改动
- 生产部署流程可能会跟着触发

一句大白话：

`push 分支 = 放上 GitHub`

`merge main = 进入主干`

`部署成功 = 线上真的跟着变`

这三件事不是一回事。

### 4.3 Actions 怎么看

GitHub Actions 主要看的是：

- 有没有红叉
- 红叉挂在哪个 job
- 是后端测试挂了，还是前端构建挂了

如果主干 Actions 红了，正常流程是：

1. 先找失败用例
2. 修代码或修测试
3. 再推一次
4. 直到恢复

不是红了就停在那等你再提醒。

## 6. 哪些情况需要直接上腾讯云

下面这些场景，经常要直接碰腾讯云：

### 6.1 数据修复

比如：

- 改某个用户持仓成本
- 改 adjustment
- 补某天快照
- 查线上 SQLite 数据

这类不是“改代码就完事”，而是：

`要碰线上数据`

### 6.2 应急修 bug

比如：

- 价格源紧急错价
- 自动快照任务挂了
- 某个服务线上异常

这类可能要：

- 先把代码发到线上
- 先重启服务
- 先让线上恢复

然后再补 GitHub。

### 6.3 巡检和验证

比如：

- 看服务状态
- 看 cron
- 看数据库
- 看日志
- 看 health

## 7. 最常见的 4 类操作

### 7.1 本地改 Flutter 页面

标准流程：

```text
改代码
-> 真机热重载
-> 你验收
-> 你说通过
-> 写版本记录
-> 推 GitHub
-> 看 Actions
```

### 7.2 本地改 Web 或后端逻辑

标准流程：

```text
改代码
-> 本地跑页面 / 接口
-> 你验收
-> 你说通过
-> 写版本记录
-> 推 GitHub
-> 看 Actions
```

### 7.3 紧急修线上价格或快照

应急流程：

```text
先查腾讯云
-> 修线上代码或修线上数据
-> 线上恢复
-> 再补本地仓库与 GitHub
```

### 7.4 纯数据修复

这类通常是：

```text
查线上数据库
-> 改数据
-> 看页面是否追平
-> 如有必要重打快照
```

这类不一定需要升版本号，但通常应该留下说明。

## 8. 你以后最实用的判断方法

以后只要问自己这 3 句，基本就知道该走哪条线：

### 问题一

这次改的是：

- 代码
还是
- 数据

### 问题二

这次需要：

- 本地验收
还是
- 直接线上修复

### 问题三

这次是不是要发新的客户端安装包

如果不是，就通常：

- 写版本记录
- 不升客户端版本号

## 9. 一句结论

你当前这套项目，最标准、最适合长期维护的操作图就是：

```text
先本地改
-> 先本地验
-> 你确认通过
-> 写版本记录
-> 推 GitHub
-> 自查 Actions
-> 再让主干和线上一致
```

而腾讯云这条线，更多是：

`应急修复、数据修复、线上排障`

不要把两条线混成一条，不然后面一定会乱。
