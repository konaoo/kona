# 请求追踪与排障手册

## 1. 先说结论

现在这个项目排接口问题，优先不要再靠猜。

统一规则是：

`先拿 request id，再回头串前端、后端、CI 和线上日志。`

如果你发现：

- 登录偶发失败
- Web 页面偶发空白
- Flutter 某个接口偶发超时
- 数据更新了但页面没刷新
- 线上用户说“刚刚不对，现在又好了”

第一反应都应该是：

1. 先找这次请求的 `request_id`
2. 再去后端日志里按同一个 `request_id` 查
3. 再判断是前端发错、后端处理错、还是部署链路有问题

## 2. 这套追踪现在覆盖到哪里

### 后端

- 所有 API 请求都会统一生成或透传 `X-Request-Id`
- 响应头会把同一个 `X-Request-Id` 回给调用方
- 后端日志会写一条摘要：
  - `request_id`
  - `method`
  - `path`
  - `status`
  - `duration_ms`
  - `user_id`
  - `ip`

对应代码：

- [request_runtime.py](/Users/kona/Desktop/kaka/kona_repo/kona_tool/request_runtime.py)

### Web

- 所有通过 [http.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/shared/http.ts) 发起的请求，都会自动补 `X-Request-Id`
- JSON 写请求如果没有 `request_id`，会自动补上
- 请求失败时，错误对象会尽量带回后端返回的 `requestId`

对应代码：

- [http.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/shared/http.ts)
- [requestTrace.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/shared/requestTrace.ts)

### Flutter

- [api_service.dart](/Users/kona/Desktop/kaka/kona_repo/flutter/lib/services/api_service.dart) 统一补 `X-Request-Id`
- 写请求会尽量保证 header 和 body 里的 `request_id` 是同一个

## 3. 真排障时怎么用

### 场景一：Web 某个接口报错

先做这几步：

1. 打开浏览器开发者工具
2. 找到失败的请求
3. 记下响应头里的 `X-Request-Id`
4. 去后端日志里搜这个值

你要找的不是“有没有报错”这么粗的判断，而是：

- 这条请求有没有真正打到后端
- 后端返回的是 `4xx` 还是 `5xx`
- 这条请求耗时是不是异常高
- 这条请求对应的是哪个用户

### 场景二：Flutter 用户说“刚刚不对”

优先看两处：

1. App 端这次请求有没有打出去
2. 后端日志里有没有同一个 `request_id`

如果后端日志里完全没有这条 `request_id`，优先怀疑：

- App 端网络
- 域名 / IP fallback
- 本地会话或 token 状态

如果后端日志里有，但状态码不对，就继续往后端查。

### 场景三：接口成功了，但页面不对

这种时候不要直接说“后端没问题”。

正确做法是：

1. 先确认接口响应成功
2. 再确认页面拿到的是不是同一份返回
3. 再确认页面有没有被缓存恢复、旧状态回填、二次刷新覆盖

这类问题最常见于：

- Web 登录恢复
- Web 页面缓存恢复
- Flutter `refreshAll`
- Flutter 启动时 `hydrateFromCache`

## 5. 线上排障时先查什么

如果线上用户说“刚刚接口不对”，默认先按这个顺序：

1. 查 GitHub Actions 最近一次是不是刚部署
2. 查服务器当前 `HEAD` 是不是目标提交
3. 查后端日志有没有对应 `request_id`
4. 查这个 `request_id` 的状态码和耗时
5. 再决定是代码问题、部署问题还是单次网络问题

不要一上来就：

- 先改代码
- 先重启服务
- 先猜数据库有问题

## 6. 最容易误判的地方

### 1. 前端报错，不等于后端一定错

有时候只是：

- token 过期
- 页面缓存恢复把旧状态顶回来了
- 用户看到的是旧 UI 状态，不是最新接口结果

### 2. 后端成功返回，不等于页面一定用上了这份数据

特别是带缓存恢复和自动刷新的页面，可能出现：

- 先拿到新数据
- 又被旧缓存回填
- 或者又被另一轮刷新覆盖

### 3. 没有 request id，不等于后端没收到

如果是老接口、直连 fetch、或异常发生得太早，有时要同时看：

- 请求头
- 响应头
- 服务端摘要日志

---

## 7. 现在这套机制解决了什么

它主要解决的是：

- 之前出了问题只能靠猜
- Web、Flutter、后端三端日志对不上
- 页面偶发问题很难知道是哪一环错了

现在至少已经做到：

- 同一条请求能跨端对上
- Web smoke 能正式防回归
- 后端日志不再只有“报错了”，而是有完整请求摘要

但要注意：

`这套机制解决的是“更容易定位”，不是“以后绝不出问题”。`

它让排障从“黑盒”变成“可查”，这已经是长期维护里非常值钱的一步。
