# 请求追踪与排障手册

## 1. 先说结论

现在这个项目排接口问题，优先不要再靠猜。

统一规则是：

`先拿 request id，再回头串前端、后端、CI 和线上日志。`

如果你发现：

- 登录偶发失败
- Web 页面偶发空白
- Flutter 某个接口偶发超时
- 数据更新了但页面没刷新
- 线上用户说“刚刚不对，现在又好了”

第一反应都应该是：

1. 先找这次请求的 `request_id`
2. 再去后端日志里按同一个 `request_id` 查
3. 再判断是前端发错、后端处理错、还是部署链路有问题

另外现在已经补了一个可直接用的脚本：

```bash
cd /Users/kona/Desktop/kaka/kona_repo
python3 scripts/request_id_trace.py req-xxxx
```

它会直接把同一个 `request_id` 对应的请求摘要和相关日志捞出来。

## 2. 这套追踪现在覆盖到哪里

### 后端

- 所有 API 请求都会统一生成或透传 `X-Request-Id`
- 响应头会把同一个 `X-Request-Id` 回给调用方
- 响应头还会补：
  - `X-Trace-Stage-Count`
  - `X-Trace-Stage-Total-Ms`
- 后端日志会写一条摘要：
  - `request_id`
  - `method`
  - `path`
  - `status`
  - `duration_ms`
  - `user_id`
  - `ip`
- 如果这条接口走了后端读侧服务，日志里还会带：
  - `stage_count`
  - `stage_total_ms`
  - `stage_gap_ms`
  - `stages`

## 3. 真排障时怎么用

### 场景一：Web 某个接口报错

先做这几步：

1. 打开浏览器开发者工具
2. 找到失败的请求
3. 记下响应头里的 `X-Request-Id`
4. 去后端日志里搜这个值

你要找的不是“有没有报错”这么粗的判断，而是：

- 这条请求有没有真正打到后端
- 后端返回的是 `4xx` 还是 `5xx`
- 这条请求耗时是不是异常高
- 这条请求对应的是哪个用户
- 如果 `X-Trace-Stage-Count > 0`，还要继续看慢的是：
  - 数据库
  - 批量取价
  - 汇率加载
- 市场状态
- 还是最后结果组装

这时候可以直接跑：

```bash
cd /Users/kona/Desktop/kaka/kona_repo
python3 scripts/request_id_trace.py 你的-request-id
```

如果是在服务器上查：

```bash
cd /opt/kaka/portfolio
python3 scripts/request_id_trace.py 你的-request-id --source journalctl --unit kona
```

### 场景二：Flutter 用户说“刚刚不对”

优先看两处：

1. App 端这次请求有没有打出去
2. 后端日志里有没有同一个 `request_id`

如果后端日志里完全没有这条 `request_id`，优先怀疑：

- App 端网络
- 域名 / IP fallback
- 本地会话或 token 状态

如果后端日志里有，但状态码不对，就继续往后端查。

### 场景三：接口成功了，但页面不对

这种时候不要直接说“后端没问题”。

正确做法是：

1. 先确认接口响应成功
2. 再确认页面拿到的是不是同一份返回
3. 再确认页面有没有被缓存恢复、旧状态回填、二次刷新覆盖

这类问题最常见于：

- Web 登录恢复
- Web 页面缓存恢复
- Flutter `refreshAll`
- Flutter 启动时 `hydrateFromCache`

### 场景四：接口成功，但就是很慢

这种时候不要再只看整条请求总耗时。

正确做法是：

1. 先看响应头里的 `X-Trace-Stage-Count`
2. 再看 `X-Trace-Stage-Total-Ms`
3. 去后端日志里搜同一个 `request_id`
4. 看 `stages=` 后面到底是哪一段最慢

常见判断方法：

- `portfolio.db` 慢，优先查数据库查询和索引
- `portfolio.quotes` 慢，优先查价格源和外部依赖
- `portfolio.rates` 慢，优先查汇率接口或缓存
- `analysis.rank.assemble` 慢，优先查后端组装逻辑是不是长胖了

如果是写接口，还要继续区分：

- `*.validate` 慢：先查前端传参和后端校验逻辑
- `*.write` 慢：先查数据库写入、锁等待、事务大小
- `*.snapshot` 慢：先查写入后触发的快照保存或后处理

### 场景五：登录异常怎么查

统一按这个顺序：

1. 先拿 `POST /api/auth/login` 或 `/api/auth/refresh` 的 `request_id`
2. 看响应码是 `400 / 401 / 403 / 500` 哪一类
3. 用脚本或日志查同一个 `request_id`
4. 看阶段停在：
   - `auth.login.lookup_user`
   - `auth.login.verify_password`
   - `auth.login.issue_tokens`
   - `auth.refresh.lookup_token`
   - `auth.refresh.lookup_user`
5. 再判断是账号密码、刷新令牌、账号状态还是发 token 这一步出了问题

### 场景六：投资页数据不对怎么查

统一按这个顺序：

1. 先分清是“读接口不对”还是“买卖写入后不对”
2. 如果是读接口，看 `/api/portfolio` 的阶段：
   - `portfolio.db`
   - `portfolio.quotes`
   - `portfolio.rates`
   - `portfolio.assemble`
3. 如果是买卖写入后不对，看写接口的阶段：
   - `portfolio.buy.write`
   - `portfolio.sell.write`
   - `portfolio.modify.write`
   - `portfolio.*.snapshot`
4. 如果写接口成功但页面还是旧数据，再回到页面缓存恢复和二次刷新链路查

### 场景七：分析页慢怎么查

统一按这个顺序：

1. 先拿 `/api/analysis/*` 的 `request_id`
2. 查日志里是概览慢、日历慢还是排行慢
3. 重点看这些阶段：
   - `analysis.overview.*`
   - `analysis.calendar.db`
   - `analysis.rank.db`
   - `analysis.rank.quotes`
   - `analysis.rank.assemble`
4. 如果主要慢在 `quotes`，优先查价格源；如果主要慢在 `assemble`，优先查后端组装逻辑

### 场景八：sync 异常怎么查

统一按这个顺序：

1. 先拿 `/api/sync/bootstrap` 的 `request_id`
2. 看是否只有某个域失败
3. 重点看这些阶段：
   - `sync.rates`
   - `sync.versions`
   - `sync.domain.cash_assets`
   - `sync.domain.portfolio`
   - `sync.market_status`
4. 如果只是单个域慢或失败，先查那一个域对应的数据接口和缓存，不要一上来怀疑整个 sync

### 场景九：用户说“刚刚不对，现在又好了”怎么查

这种最容易误判。

统一按这个顺序：

1. 先问时间点、页面、动作
2. 先定位最接近那次的 `request_id`
3. 看同一个用户在那几分钟内有没有：
   - 失败后重试成功
   - 旧缓存回填
   - 写入成功但后续刷新慢
4. 如果日志里看到同一类请求连续两次，第一次失败第二次成功，不要急着改代码，先判断是不是单次网络或上游波动

## 5. 线上排障时先查什么

如果线上用户说“刚刚接口不对”，默认先按这个顺序：

1. 查 GitHub Actions 最近一次是不是刚部署
2. 查服务器当前 `HEAD` 是不是目标提交
3. 查后端日志有没有对应 `request_id`
4. 查这个 `request_id` 的状态码和耗时
5. 再决定是代码问题、部署问题还是单次网络问题

如果已经拿到 `request_id`，优先直接用：

```bash
python3 scripts/request_id_trace.py 你的-request-id --source journalctl --unit kona
```

这样能先把相关日志收一遍，再决定要不要继续翻整段日志。

不要一上来就：

- 先改代码
- 先重启服务
- 先猜数据库有问题

## 6. 最容易误判的地方

### 1. 前端报错，不等于后端一定错

有时候只是：

- token 过期
- 页面缓存恢复把旧状态顶回来了
- 用户看到的是旧 UI 状态，不是最新接口结果

### 2. 后端成功返回，不等于页面一定用上了这份数据

特别是带缓存恢复和自动刷新的页面，可能出现：

- 先拿到新数据
- 又被旧缓存回填
- 或者又被另一轮刷新覆盖

### 3. 没有 request id，不等于后端没收到

如果是老接口、直连 fetch、或异常发生得太早，有时要同时看：

- 请求头
- 响应头
- 服务端摘要日志

### 4. 写接口成功，不等于快照和页面一定已经追平

现在很多写接口都会在成功后继续走：

- `*.snapshot`
- 页面端的 `refreshAll`
- 缓存恢复后的二次覆盖

所以“写成功了但首页还没变”，不一定是写库失败，也可能是快照或页面刷新慢了一步。
