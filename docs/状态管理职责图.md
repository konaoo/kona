# 状态管理职责图

这份文档只回答一个问题：

`项目里到底是谁在管状态，现在最该盯哪里。`

---

## 1. 先说结论

当前项目两端的状态管理形态不一样：

### Flutter

现在是：

`AppState 一把抓`

核心文件：

- [app_state.dart](/Users/kona/Desktop/kaka/kona_repo/flutter/lib/providers/app_state.dart)

### Web

现在是：

`新 stores 已接管主链路，旧 shared/store.ts 变成遗留兼容文件`

核心文件：

- [stores/composables.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/composables.ts)
- [auth.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/auth.ts)
- [portfolio.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/portfolio.ts)
- [quote.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/quote.ts)
- [market.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/market.ts)
- [sync.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/sync.ts)

一句大白话：

`Flutter 是一个总管太大，Web 是主入口已经统一，但旧壳子还没完全退役。`

---

## 2. Flutter 现在谁在管状态

Flutter 几乎所有全局状态都集中在：

- [app_state.dart](/Users/kona/Desktop/kaka/kona_repo/flutter/lib/providers/app_state.dart)

它现在承担的主要职责有：

- 认证与安全
- 资产与持仓
- 汇率、市场与行情
- 历史概览与同步
- UI 偏好
- 非投资资产操作
- 投资交易操作

### 2.1 Flutter 当前优点

- 查问题快
- 页面拿数据简单
- 缓存、刷新、收益口径能串起来看

### 2.2 Flutter 当前风险

最大问题还是：

`AppState 太大`

这意味着：

- 文件会继续变长
- 改一处容易牵一片
- 后面拆分时成本会越来越高

---

## 3. Web 现在谁在管状态

### 3.1 页面统一入口

现在页面、布局、路由统一走：

- [stores/composables.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/composables.ts)

它的作用很明确：

`把多个新 stores 重新拼成一个页面好接的统一入口。`

### 3.2 新 stores 的职责

- [auth.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/auth.ts)
  - 登录、用户、token

- [portfolio.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/portfolio.ts)
  - 持仓、行数据、收益计算结果

- [quote.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/quote.ts)
  - 行情、自动刷新、报价节奏

- [market.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/market.ts)
  - 汇率、市场开闭状态

- [sync.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/stores/sync.ts)
  - bootstrap、版本、缓存、增量刷新

### 3.3 旧 store 现在是什么角色

旧文件还在：

- [shared/store.ts](/Users/kona/Desktop/kaka/kona_repo/web/src/shared/store.ts)

但它现在已经不是页面直接入口。

它更像：

`历史遗留兼容文件`

不是：

`未来还要继续扩展的正式状态中心`

---

## 4. 当前最该警惕的重复

### 4.1 Web 仓库里仍能看到两套入口

虽然页面主链路已经统一，但仓库里仍然同时存在：

- `shared/store.ts`
- `stores/composables.ts`

这会带来一个维护风险：

`后面的人不一定知道该接哪一个。`

### 4.2 Flutter 没有双轨，但有“大一统”

Flutter 没有 Web 那种新旧两套同时当入口的问题。

它的问题更单纯：

`AppState 太大，后面拆分成本会越来越高。`

---

## 5. 现在最合理的治理顺序

### 5.1 先守住 Web

Web 现在最该做的不是继续大迁移，而是守住边界：

1. 新页面默认只接新 stores
2. `shared/store.ts` 不再加新职责
3. 未来找时机退役旧文件

### 5.2 Flutter 先不急着拆

Flutter 现在更适合：

1. 继续按职责分段
2. 明确每组方法归属
3. 等结构和认知完全稳定后，再考虑拆 Provider / Service

---

## 6. 你现在最该记住的 4 句话

1. Flutter 的问题是 `一个总管太大`
2. Web 的问题是 `主链路收口了，但旧壳子还留着`
3. Web 现在最重要的是 `冻结旧 store`
4. Flutter 现在最重要的是 `继续把职责边界写清楚`

---

## 7. 一句结论

当前项目的状态层已经比之前清楚很多了。

现在真正要做的，不是盲目大拆，而是：

`Web 先把遗留边界钉死，Flutter 再按分组慢慢收。`
