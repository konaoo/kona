# 投资持仓修正与收益事件迁移说明

## 1. 先说结论

从 `2026-03-20` 这一轮开始，投资持仓这块的主口径已经改了：

1. `transactions` 只记录真正的交易
   - `加仓`
   - `减仓`
2. `portfolio_adjustment_ledger` 只记录非交易收益事件
   - `分红`
   - `手续费`
   - `税`
3. `portfolio_correction_logs` 只记录“修正当前持仓状态”
   - 成本价修正
   - 数量修正
   - 同时修正成本价和数量
4. 页面显示成本价，统一直接认 `portfolio.price`
   - 不再用 `adjustment` 摊薄
5. `portfolio.adjustment` 现在只剩旧兼容意义
   - 新写入逻辑不再继续依赖它

一句大白话：

`交易是交易，收益事件是收益事件，修正是修正，三条线现在正式拆开了。`

---

## 2. 现在每张表各管什么

### 2.1 `portfolio`

这张表只表示“当前这只持仓现在是什么状态”。

关键字段：

- `code`
- `name`
- `qty`
- `price`
- `curr`
- `asset_type`
- `user_id`

这里的：

- `qty` = 当前剩余持仓数量
- `price` = 当前剩余持仓的成本单价

### 2.2 `transactions`

这张表只记交易动作。

现在只允许两种：

- `加仓`
- `减仓`

字段含义：

- `price` = 当次成交价
- `qty` = 当次成交数量
- `amount` = 当次成交金额
- `pnl`
  - 加仓固定是 `0`
  - 减仓表示这次卖出的已实现盈亏
- `curr` = 这笔交易对应资产的币种
- `market` = 这笔交易对应的市场归类
- `effective_date` = 这笔交易真正归属到哪一天

从这轮开始，新写入交易会直接把这 3 个字段记下来。

一句大白话：

`以后不是每次读交易再现场猜“这笔到底算哪天、算哪个市场”，而是新交易写进去时就把这件事记清楚。`

### 2.3 `portfolio_adjustment_ledger`

这张表现在只记非交易收益事件。

允许类型：

- `dividend`
- `fee`
- `tax`

规则：

- 分红只写这里
- 手续费只写这里
- 税只写这里
- 这些事件不改 `portfolio.price`
- 这些事件不改 `portfolio.qty`

### 2.4 `portfolio_correction_logs`

这张表专门记录“当前持仓被修正过什么”。

允许类型：

- `opening_balance`
- `cost_price`
- `quantity`
- `holding`

规则：

- 直接新增一只持仓：写 `opening_balance`
- 修正成本价：改 `portfolio.price`，同时写一条修正日志
- 修正数量：改 `portfolio.qty`，同时写一条修正日志
- 同时改数量和成本价：写 `holding`

这张表的用途有两个：

1. 给用户看历史修正记录
2. 给排障时看是谁把当前持仓状态改了

现在还多了一层意义：

3. 给“不是交易买出来的初始持仓”补一个明确来源事件

一句大白话：

`以后手工新加一只持仓，不会再只有当前结果，没有起点记录。`

## 3. 当前读侧怎么算

### 3.1 成本价

当前页面显示成本价：

`直接等于 portfolio.price`

不再走旧的：

`((price * qty) - adjustment) / qty`

### 3.2 累计盈亏

当前累计盈亏应该理解成 3 段相加：

1. 浮动盈亏
   - `current_value - portfolio.price * portfolio.qty`
2. 已实现盈亏
   - 所有减仓交易的 `transactions.pnl` 汇总
3. 现金类收益事件
   - `dividend - fee - tax`

### 3.3 为什么分红不该再改成本价

因为分红是现金收益，不是你当前剩余仓位的买入成本变化。

所以现在正确行为是：

- 加分红
  - 累计盈亏会上升
  - 成本价不变

- 加手续费
  - 累计盈亏会下降
  - 成本价不变

## 4. 旧 `adjustment` 现在怎么处理

### 4.1 现状

旧数据里还有一部分历史值仍然在 `portfolio.adjustment`。

这部分值还保留着，是因为：

1. 老版本长期把很多东西都混在这里
2. 直接清掉会让历史累计盈亏瞬间跳变

### 4.2 当前原则

现在的原则是：

- 新逻辑不再往这里继续写新语义
- 读侧暂时还兼容它
- 但它已经不是“未来唯一真相”

### 4.3 后续迁移建议

后面如果要彻底清理旧口径，建议按这条顺序做：

1. 先冻结旧写法
   - 不再让任何新功能继续写 `portfolio.adjustment`
2. 再识别旧值来源
   - 哪些是历史分红
   - 哪些是历史手续费
   - 哪些是旧手工补差
3. 能迁就迁
   - 分红/手续费迁到 `portfolio_adjustment_ledger`
   - 修正痕迹迁到 `portfolio_correction_logs`
4. 识别不了的旧值先保守保留
   - 不编造历史明细
5. 最后再决定是否停止读侧兼容 `portfolio.adjustment`

一句话：

`先停继续写脏数据，再慢慢迁旧数据，不要反过来。`

### 4.4 现在新增了一层“迁移盘点”

这轮没有直接迁旧数据，也没有自动切用户开关。

先补的是：

1. 后端可生成单用户迁移盘点
   - 看当前还有几只持仓带旧 `adjustment`
   - 看旧值合计是多少
   - 看这只资产有没有交易、收益事件、修正记录
2. 本地脚本可扫整库
   - 脚本：`kona_tool/scripts/audit_portfolio_legacy_adjustment.py`
   - 默认只读，不写库

它的目的只有一个：

`先把“谁能直接切、谁必须人工看”分出来，再决定后面怎么迁。`

## 6. 详情页现在应该看到什么

### 6.1 保存修正后

详情页交易记录应出现：

- `成本修正`
- `数量修正`
- `持仓修正`

并且文案会直接展示变化前后：

- `成本价 2 -> 2.1`
- `持仓数量 100股 -> 120股`

### 6.2 同一秒多条记录

现在列表统一按：

- 时间倒序
- 同秒再按 `id` 倒序

所以不会再出现“同一秒新增的手续费排到分红后面”这种顺序抖动。

## 7. 排查时先看哪几张表

如果以后再遇到“投资详情页不对”，优先按这个顺序查：

1. 看 `portfolio`
   - 当前持仓数量和成本价是不是对
2. 看 `transactions`
   - 加仓 / 减仓有没有写进去
3. 看 `portfolio_adjustment_ledger`
   - 分红 / 手续费 / 税有没有写进去
4. 看 `portfolio_correction_logs`
   - 修正记录有没有写进去

如果是指定真实用户的数据问题，默认优先查线上库，不看本地库下结论。
