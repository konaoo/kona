# 手机端访问改造成类 Flutter 体验方案

这份文档是给后续接手的 AI 或开发同学看的。

目标不是重做整站，也不是把现有 Web 换成 Flutter Web。

目标只有一个：

`保留当前桌面 Web 端，单独把手机浏览器访问做成尽量沿用 Flutter App 页面、交互和 UI 的体验。`

---

## 1. 先说结论

这件事可行。

但正确做法不是：

- 把现在的 Vue Web 整体替换成 Flutter Web
- 或者同时维护两套完全独立的业务逻辑

而是：

`继续保留当前 Web 技术栈，只给手机访问增加一套移动端视图层。`

也就是说：

- 桌面端：继续用现在这套 Web 页面
- 手机浏览器：走移动端专属页面布局和交互
- 后端接口：继续复用现在的接口
- 业务口径：继续复用现在的口径

一句话：

`改展示层，不重写业务层。`

---

## 2. 这次要解决什么问题

现在的问题不是“Web 不能在手机上打开”。

现在的问题是：

- 手机浏览器打开 Web 后，体验不像 App
- 布局、密度、交互节奏都更像桌面网页
- 用户会觉得“这不是一个适合手机使用的产品”

而 Flutter 端已经有一套更成熟的移动端视觉和交互语言。

所以这次改造的目标是：

- 手机上的 Web，看起来更像 Flutter
- 手机上的 Web，用起来也尽量像 Flutter
- 页面结构、交互方式、视觉层级优先对齐 Flutter
- 但不要因此把现有 Web 架构打散

### 2.1 Flutter 参考规则

后续 AI 默认必须把 Flutter 端当成这次移动端 Web 改造的唯一主参考稿。

这句话的意思是：

- 手机端 Web 不是自由发挥做一套“新的 H5”
- 不是“只要差不多像 App 就行”
- 而是：

`优先沿用 Flutter 现有页面结构、交互方式和 UI 语言。`

默认执行规则：

1. 页面模块顺序优先对齐 Flutter
2. 主按钮位置优先对齐 Flutter
3. 交互流程优先对齐 Flutter
4. 卡片结构、信息层级、留白节奏优先对齐 Flutter
5. 只有浏览器环境确实受限时，才允许做 Web 化调整

一句话：

`先像 Flutter，再像普通手机网页。`

---

## 3. 绝对不要这么做

后续 AI 默认不要走下面这些路：

### 3.1 不要直接把现有 Web 全换成 Flutter Web

原因：

- 当前项目已经有成熟的 Vue Web
- 管理后台也是 Web
- Flutter Web 会增加另一套前端打包、兼容和调试复杂度
- 首屏大小、浏览器体验、SEO、分享、页面适配不一定更好

### 3.2 不要复制一套后端接口

不能做成：

- 桌面 Web 一套接口
- 手机 Web 再新开一套接口

正确做法是：

- 继续复用现有接口
- 只改视图层和前端状态组织

### 3.3 不要为了像 Flutter，就把 Web 写成“假 App 壳”

例如：

- 到处写死高度
- 大量绝对定位
- 全站只考虑一个手机宽度
- 只追求像截图，不考虑浏览器真实行为

要记住：

- 它还是 Web
- 只是体验尽量像 Flutter

### 3.4 不要脱离 Flutter 重新设计一套移动端产品

这次手机端 Web 改造，不是让 AI 重新发明一套手机端产品。

默认不允许：

- Flutter 是 A 布局，Web 手机端自己改成 B 布局
- Flutter 是底部导航，Web 手机端自己改成顶部复杂导航
- Flutter 已经有成熟交互，Web 手机端重新发明
- Flutter 是卡片流，Web 手机端改成表格流

一句话：

`手机端 Web 要先对齐 Flutter，不要先追求“做个新的移动网页”。`

## 4. 推荐架构

推荐方案：

`同一套 Vue Web + 同一套路由体系 + 同一套接口 + 按设备切换桌面视图 / Flutter 风格移动视图`

### 4.1 总体结构

建议分成两层：

1. 业务层
   - 继续沿用现有状态和接口
   - 不重复写

2. 视图层
   - 桌面视图继续保留
   - 手机视图新增一套移动端布局

### 4.2 建议的代码组织方式

不要直接在一个页面里写满：

- `if mobile`
- `if desktop`
- `if smallScreen`

这样后面会很快变成屎山。

建议做法：

- 页面级容器负责判断当前是桌面还是手机
- 然后分别渲染：
  - `DesktopView`
  - `MobileView`

例如：

```ts
AppHomePage.vue
  -> AppHomeDesktop.vue
  -> AppHomeMobile.vue
```

同理：

- `AppInvestPage.vue`
- `AppAnalysisPage.vue`
- `AppMePage.vue`

都可以用这种拆法。

### 4.3 不要拆出第二套 store

状态层继续用现在已有的主入口：

- `/Users/kona/Desktop/kaka/kona_repo/web/src/stores/composables.ts`

不要为了移动端再开：

- `mobileStore`
- `appMobileState`
- `flutterLikeStore`

一句话：

`移动端只换页面，不换状态主入口。`

---

## 5. 路由策略

### 5.1 不建议新开一套 /m 路由

例如不建议直接做：

- `/m/home`
- `/m/invest`

因为这会让：

- 同一个产品有两套路由
- 维护成本更高
- 分享和跳转逻辑更乱

### 5.2 推荐沿用原路由，按宽度切视图

比如：

- `/app/home`
- `/app/invest`
- `/app/analysis`
- `/app/me`

在这些路由内部：

- 桌面宽度走桌面布局
- 手机宽度走移动布局

### 5.3 管理后台不需要手机化

管理后台继续桌面优先。

这次改造范围不包含：

- `/admin/*`

除非主人后续明确要求。

---

## 6. 哪些页面应该先做

建议按 MVP 顺序做，不要一口气全改。

### 第一阶段：核心 4 页

1. 登录页
2. 首页
3. 投资页
4. 我的页面

这是最先该做成“像 Flutter”的部分。

因为用户最常看的就是这几页。

### 第二阶段：次核心页

1. 分析页
2. 资产详情页
3. 录入 / 编辑资产页
4. 登录后的设置页

### 第三阶段：再考虑其他长尾页

如果前两阶段没做稳，不要继续扩。

---

## 7. 视觉和交互应该怎么像 Flutter

目标不是做成“普通响应式网页”。

目标是让用户感觉：

`这就是 Flutter 那个 App 的浏览器版。`

### 7.1 页面结构

手机 Web 视图建议统一成：

- 顶部状态区更紧凑
- 内容卡片更高、更圆角
- 统一 16 / 20 / 24 的内边距节奏
- 更明显的主卡 / 次卡层级

### 7.2 导航方式

推荐做成：

- 底部 Tab 导航

而不是桌面端那种：

- 侧边栏
- 顶部功能按钮堆一起

手机端底部 Tab 更接近 Flutter App 体验。

### 7.3 交互节奏

手机端要更像 App，就要尽量避免：

- 同页展开太多内容
- 一屏信息过密
- 多层表格

建议更多使用：

- 卡片
- 底部弹层
- 全屏弹层
- 分段切换

### 7.4 字体和点击区域

手机端所有可点区域必须放大：

- 按钮高度不低于 44px
- 图标按钮不低于 40px
- 输入框不低于 48px

### 7.5 动效

建议保留少量：

- 页面切入
- 卡片出现
- 底部弹层展开

不要为了像 App，把一堆花哨动效硬塞进去。

---

## 8. 数据和接口怎么处理

### 8.1 一律复用现有接口

不要新开移动端专属接口，除非：

- 桌面接口一次返回太多无用字段
- 明显拖慢手机端首屏

默认原则：

`先复用，后优化。`

### 8.2 现有业务口径不要重算

例如：

- 价格
- 收益
- 快照
- 总资产
- 建账期
- 趋势图

这些都继续以现有后端口径为准。

不要因为换成移动端页面，就让前端自己再算一套。

### 8.3 趋势图继续复用现有逻辑

首页总资产图和持仓小趋势图，现在已经有真实数据口径。

手机端应该做的是：

- 换显示方式
- 换布局
- 换交互密度

不要再新做一套“移动端趋势算法”。

---

## 9. 设备判断怎么做

推荐做一个统一的移动端判断入口。

不要每个页面自己写：

- `window.innerWidth < 768`
- `navigator.userAgent`
- `matchMedia`

建议统一抽到一个 composable 里，例如：

- `useDeviceView()`

返回：

- `isMobile`
- `isTablet`
- `isDesktop`

页面只消费，不自己判断。

### 9.1 判定建议

优先用：

- 宽度
- 触摸环境
- 响应式断点

不要过度依赖 UA 字符串。

因为：

- 浏览器 UA 太容易不稳定
- 平板和折叠屏会很乱

---

## 10. 推荐实施步骤

### 第一步：先把首页做成移动版

原因：

- 最能看出成色
- 用户第一感知最强
- 也最适合跟 Flutter 对齐

这一阶段完成后要能做到：

- 手机上的 `/app/home` 明显不是桌面网页缩放版
- 而是专门的移动端首页

### 第二步：做投资页

因为：

- 投资页是第二高频页
- 这里最容易暴露桌面逻辑硬塞到手机的问题

### 第三步：补底部导航和我的页

到这一步，手机端才会真正像一个 App。

### 第四步：再做分析页和详情页

不要一开始就啃最复杂的图表页。

---

## 11. 明确的验收标准

后续 AI 做完后，至少要按下面这套验收。

### 11.1 首页

- 手机宽度下，首页必须是移动布局
- 总资产卡、趋势图、资产分区不能是桌面压缩版
- 操作按钮大小适合手指点
- 趋势图和建账期口径不变

### 11.2 投资页

- 卡片、列表、筛选都要是移动布局
- 长名称不应溢出
- 持仓卡和趋势图都要适配小屏

### 11.3 登录页

- 输入框、按钮、错误提示都适合手机阅读
- 不要出现桌面风格留白过大

### 11.4 导航

- 手机端必须有更像 App 的主导航
- 不允许继续使用桌面侧边栏思路

### 11.5 性能

- 手机端首屏不能明显卡顿
- 不要因为“像 Flutter”就把图片、阴影、动画做得太重

## 12. 技术注意事项

### 12.1 不要直接改坏桌面端

这次是：

- 新增手机端视图
- 不是重做桌面端

桌面端现有页面要尽量保持稳定。

### 12.2 不要把移动端样式写进全局污染桌面

优先：

- 页面内局部样式
- 组件级样式
- 明确断点控制

不要为了方便，在全局 CSS 里乱压。

### 12.3 不要复制一套业务组件再长期分叉

比如不要出现：

- `PositionCardDesktop.vue`
- `PositionCardMobile.vue`
- 然后里面业务逻辑各写一半

更稳的方式是：

- 同一份数据逻辑
- 外层切布局

### 12.4 不要为了手机端继续加更多页面内计算

移动端如果需要更轻的展示：

- 优先裁剪展示
- 不要前端重新计算收益、价格、汇率

### 12.5 录入和编辑弹窗在手机端要重做成更合适的层

手机浏览器上，很多桌面弹窗不适合直接复用。

建议：

- 抽屉
- 底部弹层
- 全屏表单页

不要把桌面大弹窗强塞到手机里。

## 13. 后续 AI 必须遵守的边界

后续接手的 AI 默认必须遵守这些边界：

1. 不要把这次改造理解成“切到 Flutter Web”
2. 不要重写后端接口
3. 不要拆第二套状态主入口
4. 不要新开 `/m/*` 路由，除非主人明确要求
5. 不要先全站铺开，先做核心 4 页
6. 不要因为手机端改造，顺手重构管理后台
7. 每做完一页，都必须本地手机尺寸验收
8. 手机端 Web 默认以 Flutter 页面作为唯一主参考稿，不要自行改成另一套产品结构

---

## 13.1 Git 分支规则

这次手机端 Web 改造，默认不要直接在 `main` 上写。

默认流程应该是：

1. 新开 `codex/` 前缀分支
2. 在分支里完成开发
3. 在分支里本地验收
4. 主人确认通过后，再决定是否合主干

推荐分支名：

- `codex/mobile-web-flutter-parity`

默认不允许：

- 还没验收，就直接把这类大改写进 `main`
- 一边做手机端改造，一边把桌面端无关改动混进主干

一句话：

`手机端 Web 改造默认走分支开发、分支验收，不碰主干。`

## 15. 最终拍板建议

如果后续 AI 需要一句最简执行原则，就按这句：

`保留当前 Web 业务层和接口层，只为手机浏览器新增一套更像 Flutter 的移动端视图。`

不要误解成：

- 另起一个 Flutter Web 项目
- 另做一套移动端接口
- 或直接把桌面 Web 打碎重写

这次正确方向是：

`同一产品、同一后端、同一状态层，移动端只换视图和交互。`
